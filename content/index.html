COMPLEX.md

A simple, open file that shows coding agents which parts of your codebase are most likely to break.

Think of COMPLEX.md as a risk map for agents. It is computed from your repository's own history, so it knows which files break most often, which files everything else depends on, and which files change together.

Why COMPLEX.md?

AGENTS.md tells a coding agent how to work in your project: how to build it, how to test it, what the rules are. A person writes it from memory.

COMPLEX.md answers a different question: where is the danger? Every codebase has a few files that break again and again, a few files that everything else depends on, and pairs of files that have to change together. People who have worked on the project for years know these files by heart. A coding agent starting fresh does not, so it edits them like any other file and the same bugs come back.

COMPLEX.md is measured, not remembered. It reads the repository's own history and dependency graph and writes down what it finds, with the numbers to prove it and one clear instruction per risky file.

  • Points agents at the files that break most often, before they start looking.
  • Warns them before they touch a file that dozens of other files depend on.
  • Shows which files change together, so a fix is never left half done.

Every number in the example above comes from a real run on the fastify web framework. Nothing is made up, the analysis runs on your own machine in about a second, and nothing is uploaded.

How to use COMPLEX.md?

1. Run it once in your repository

Open a terminal in any git repository and run npx complex-md. It reads the history and the dependency graph, writes COMPLEX.md at the root of the repository, and connects it to the agents you already use. If you have an API key for a model provider, it uses that to write the prose. If not, it hands the job to the coding agent you are already talking to.

2. Or run the skill with any agent

No Node.js? Download one markdown file and ask your coding agent to run it. The agent does the same analysis with git and writes the file itself.

3. Let the wiring do its job

The file is only useful if the agent reads it, so the tool sets that up for you:

  • A short block in AGENTS.md or CLAUDE.md that tells the agent when to look at the map.
  • Rules that switch on only when the agent opens one of the risky files.
  • For agents that support it, a hook that pauses the first edit to a risky file until the agent has read why it is risky.
  • A small server the agent can ask questions like "which files does this one affect?" while it works.

4. Run it again after big changes

The map is cheap to rebuild. After a refactor of a listed file, run the command again and commit the new COMPLEX.md with your change.

About

COMPLEX.md is built by James L. Cowan Jr. and released as open source under the MIT license: the spec, the command line tool and benchmark, and the skill.

The spec changes by evidence. Every signal in the file is backed by published research on where bugs come from, and every claim about what the file does for an agent is measured in the repository's benchmark rather than asserted.

This site's design follows agents.md (MIT), because a file for agents should look like the file agents already know.

FAQ

How is this different from AGENTS.md?

They work together. AGENTS.md is written by a person and says how to work in the project. COMPLEX.md is computed from the project and says where the risk is. The wiring step links the two, so an agent that reads one finds the other.

Do I need an API key?

No. With a key from any of eleven providers, the tool makes one model call to write the explanations. Without a key, it writes a prompt file and the coding agent you are already using writes COMPLEX.md itself. Either way, the analysis of your code never leaves your machine.

What does the score mean?

It is a ranking, not a prediction. A higher score means an edit to that file has more ways to go wrong: the file changes often, it has needed fixes before, and many other files depend on it. The spec shows the exact formula and states plainly what the analysis can and cannot see.

What if my project uses a language it cannot read?

The file says so. Files the analysis could not follow are listed under blind_spots with counts, and when they make up most of the project, the file says its ranking rests on history and size alone.

Can I write one by hand?

Yes. The format is plain markdown with a YAML header, and the spec describes every field. There is an article that walks through it with seven git commands.

How do I keep it out of my agent's way?

Run npx complex-md --no-hooks to skip the edit gate, or --no-wire to only write the file. Everything the tool adds to your agent files is marked and safe to remove.
